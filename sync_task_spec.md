# Sync Task Specification — ReadList

## Purpose
Обеспечить офлайн-режим для «Списка чтения» в Android WebView.
Локальная SQLite БД на телефоне — источник истины для отображения.
Фоновая асинхронная синхронизация синхронизирует локальные данные с сервером.

## Architecture

```
Display ← Local SQLite (ReadListDB.java)
            ↕ фоновая синхронизация
         Server PostgreSQL (read_list)
```

- Все операции чтения идут из локальной SQLite БД.
- Все мутации (create/update/delete) пишут в локальную SQLite БД + ставят `updated_at`.
- После каждой мутации автоматически запускается синхронизация.
- Синхронизация также запускается при старте приложения.
- Синхронизация асинхронная, не блокирует UI.
- Конфликты разрешаются по принципу last-write-wins (по полю `updated_at`).

## User-Scoping (Current User)

Все операции синхронизации привязаны к текущему пользователю (под чьей УЗ выполнен вход в приложение).

### Определение текущего пользователя
- `authUser` — глобальная переменная из `auth.js`, загруженная из `localStorage['auth_user']`.
- Поле `authUser.ID` — числовой ID пользователя на сервере.
- Если `authUser` не задан (не авторизован) — синхронизация не запускается, `#mobileUserBtn` красный.

### User-ID в локальной БД
- Каждая запись в `readlist_items` имеет поле `user_id` (INTEGER).
- При создании новой записи локально: `user_id = authUser.ID`.
- При Pull-синхронизации: для всех записей, полученных с сервера, `user_id = authUser.ID`.

### Фильтрация при Push
- В Push-фазе обрабатываются только dirty-записи, где `item.user_id === currentUserId`.
- Записи с `user_id`, не совпадающим с текущим пользователем, игнорируются при Push.
- Это предотвращает случайную отправку на сервер записей, созданных под другой УЗ.

### Очистка при смене пользователя
- При старте приложения (и после каждого логина) проверяется `authUser.ID`.
- Если ID текущего пользователя не совпадает с ID в локальных записях:
  - Все записи с чужим `user_id` удаляются из локальной БД.
  - Затем выполняется Pull с сервера для текущего пользователя.
- Если локальная БД пуста — это считается новым пользователем, Pull заполнит данными.

### Локальная таблица `readlist_items`
Полная копия полей с сервера + служебные:
- `id` TEXT PRIMARY KEY — UUID
- `listname`, `bookname`, `author`, `priority`, `comment`, `status`
- `author_id`, `book_id`, `edition_id`, `user_id`
- `format_name`, `on_shelf`
- `created_at` TEXT — дата создания (с сервера или локально)
- `updated_at` TEXT — локальное время последнего изменения
- `synced_at` TEXT — время последней успешной синхронизации с сервером (NULL = никогда)

### Таблица `offline_queue`
Не используется — dirty-флаги заменены сравнением `updated_at > synced_at`.

## Sync Algorithm

Синхронизация выполняется в фоне (async/await), не блокирует интерфейс.

### Шаг 1. Push (отправить локальные изменения на сервер)
```
Для всех локальных записей, где updated_at > synced_at (dirty):
  1.1. Если запись есть на сервере (проверяем HTTP 200 на GET /api/v1/user/readlist/{id}):
         PUT /api/v1/user/readlist/{id}  (body: вся запись)
       Если сервер ответил 404 (запись удалена на сервере):
         POST /api/v1/user/readlist (body: вся запись, сервер создаст заново)
       Если сервер ответил 200/201:
         обновить synced_at = updated_at
  1.2. Если записи нет на сервере (первая синхронизация):
         POST /api/v1/user/readlist (body: вся запись)
         Если сервер ответил 201:
           обновить synced_at = updated_at
  1.3. Если сервер ответил ошибкой — остановить push, перейти к шагу 2
```

### Шаг 2. Pull (забрать изменения с сервера)
```
GET /api/v1/user/readlist?limit=9999

Для каждой записи из ответа сервера:
  2.1. Если записи нет в локальной БД:
         INSERT в локальную БД (synced_at = серверный updated_at)
  2.2. Если запись есть в локальной БД:
         Если сервер.updated_at > локальный.synced_at:
           UPDATE локальной записи из серверных данных (synced_at = серверный updated_at)
         Иначе (локальная новее или synced_at актуален):
           ничего не делаем, локальная версия уже отправлена

Для всех локальных записей, которых нет в ответе сервера (удалены на сервере):
  2.3. Если локальная dirty (updated_at > synced_at):
         повторный POST на сервер (восстановить)
       Иначе:
         DELETE из локальной БД
```

### Шаг 3. Обновить UI
```
После завершения Push+Pull:
  - Если readlist-вкладка активна — перезагрузить список из локальной БД
  - Обновить цветовой индикатор #mobileUserBtn:
      synced → зелёный
      syncing → жёлтый
      error → красный
```

## Запуск синхронизации

| Событие | Действие |
|---------|----------|
| Старт приложения (DOMContentLoaded, Android) | Запустить синхронизацию |
| После create/update/delete локальной записи | Запустить синхронизацию |
| Онлайн-событие (navigator.onLine) | Запустить синхронизацию |

Синхронизация не запускается повторно, пока предыдущая не завершилась (флаг `_syncing`).
Если синхронизация уже идёт — запрос игнорируется.

## Индикация

- `#mobileUserBtn`:
  - 🟢 sync-ok — зелёный: онлайн, всё синхронизировано
  - 🟡 sync-syncing — жёлтый: идёт синхронизация
  - 🔴 sync-offline — красный: нет соединения или ошибка синхронизации
- `#pendingCount` — счётчик dirty-записей (updated_at > synced_at), показывается в фильтрах
- Кнопка `#syncReadlistBtn` — принудительная синхронизация (только если есть dirty)

## Исключения

- Если на сервере нет записей для пользователя (пустой список) — локальные dirty-записи создаются на сервере.
- Если сервер недоступен — синхронизация прерывается, dirty-записи остаются локально, индикатор красный.
- При конфликте (локальная и серверная записи изменены) побеждает более поздняя по updated_at.
- Если updated_at совпадает — побеждает локальная версия.
